# ERC20 and Reentrancy Lane

## Coverage

- Inherited ERC4626 deposit/mint: `TokenizedStrategy.deposit` and `mint` are `nonReentrant` (`lib/tokenized-strategy/src/TokenizedStrategy.sol:487-535`). `_deposit` pulls WETH with `safeTransferFrom`, calls `deployFunds` through `IBaseStrategy(address(this))`, then credits `S.totalAssets` and mints shares (`lib/tokenized-strategy/src/TokenizedStrategy.sol:954-978`). The callback is `onlySelf` in `BaseStrategy.deployFunds` (`lib/tokenized-strategy/src/BaseStrategy.sol:375-377`) and reaches `BaseLSTAccumulator._deployFunds`, which stakes if enabled (`src/BaseLSTAccumulator.sol:109-112`).
- Stake path: `Strategy._stake` unwraps WETH to ETH, reads Curve `get_dy`, then either swaps ETH to stETH with `_min_to_amount = amount` or submits to Lido (`src/Strategy.sol:51-69`). `Strategy4626._stake` then wraps all stETH to wstETH and deposits all wstETH into the configured ERC4626 vault (`src/Strategy4626.sol:29-42`).
- Withdraw/free/swap path: inherited `withdraw`/`redeem` are `nonReentrant` (`lib/tokenized-strategy/src/TokenizedStrategy.sol:565-635`). `_withdraw` can call `freeFunds` if idle WETH is short, then burns shares and transfers WETH with `safeTransfer` (`lib/tokenized-strategy/src/TokenizedStrategy.sol:989-1049`). The base strategy intentionally leaves `_freeFunds` empty (`src/BaseLSTAccumulator.sol:115-123`). Manual management swap calls `_swapLSTToAsset` (`src/BaseLSTAccumulator.sol:241-245`), which approves stETH to Curve, swaps stETH to ETH, then wraps all ETH to WETH (`src/Strategy.sol:74-82`). Strategy4626 first redeems vault shares and unwraps wstETH in `_freeStETH` (`src/Strategy4626.sol:77-96`).
- Queue/claim path: management `initiateLSTWithdrawal` increments `pendingRedemptions` before calling `_initiateLSTWithdrawal` (`src/BaseLSTAccumulator.sol:259-263`). The stETH implementation approves the Lido queue and calls `requestWithdrawals`, then ABI-encodes the returned request id array (`src/Strategy.sol:91-99`). Keeper `claimLSTWithdrawal` calls `_claimLSTWithdrawal` and subtracts the redeemed amount (`src/BaseLSTAccumulator.sol:269-272`). The stETH claim implementation decodes a single `uint256`, calls `claimWithdrawal`, computes the ETH delta, then wraps the whole ETH balance (`src/Strategy.sol:104-112`). Emergency `manualClaimWithdrawals` calls the batch queue claim, optionally zeros pending redemptions, then wraps ETH (`src/Strategy.sol:116-125`).
- Report/tend path: inherited `report` and `tend` are `nonReentrant` and keeper-gated (`lib/tokenized-strategy/src/TokenizedStrategy.sol:1081-1096`, `lib/tokenized-strategy/src/TokenizedStrategy.sol:1314-1318`). Health check wraps `_harvestAndReport` (`lib/tokenized-strategy-periphery/src/Bases/HealthCheck/BaseHealthCheck.sol:117-127`). The strategy blocks reports while `pendingRedemptions != 0`, stakes loose WETH up to available capacity, and reports `estimatedTotalAssets` (`src/BaseLSTAccumulator.sol:146-155`). TokenizedStrategy can call the Yearn factory for protocol fee config only when performance fees are charged (`lib/tokenized-strategy/src/TokenizedStrategy.sol:1132-1136`).
- Factory flow: `newStrategy4626` checks `deployments[_vault]`, reads `ERC20(_vault).symbol()`, deploys `Strategy4626`, calls the new strategy setters, emits, then stores `deployments[_vault]` (`src/Strategy4626Factory.sol:43-69`). `setAddresses` is gated by current factory management (`src/Strategy4626Factory.sol:72-83`).
- Token/approval handling: local code uses OZ `SafeERC20.forceApprove` for WETH/stETH/wstETH approvals (`src/Strategy.sol:33`, `src/Strategy.sol:75`, `src/Strategy.sol:92`, `src/Strategy4626.sol:25-26`). OZ `forceApprove` tries the target allowance then falls back to zero-reset (`lib/openzeppelin-contracts/contracts/token/ERC20/utils/SafeERC20.sol:82-88`), and safe transfers accept no-return ERC20s but reject explicit false returns (`lib/openzeppelin-contracts/contracts/token/ERC20/utils/SafeERC20.sol:117-123`, `lib/openzeppelin-contracts/contracts/token/ERC20/utils/SafeERC20.sol:139-141`).
- ETH receive behavior: `Strategy.receive()` accepts ETH from anyone (`src/Strategy.sol:36`). Claim/swap flows wrap the full ETH balance to WETH after queue/Curve interactions (`src/Strategy.sol:81`, `src/Strategy.sol:112`, `src/Strategy.sol:125`).

## Candidates

### MEDIUM - Lido queue claim data returned by `initiateLSTWithdrawal` does not match `claimLSTWithdrawal` decoding

`Strategy._initiateLSTWithdrawal` returns `abi.encode(requestIds)` where `requestIds` is a dynamic `uint256[]` from `requestWithdrawals` (`src/Strategy.sol:91-99`). The paired keeper path `Strategy._claimLSTWithdrawal` decodes `_claimData` as a single `uint256` (`src/Strategy.sol:104-108`). Passing the bytes returned by `initiateLSTWithdrawal` into `claimLSTWithdrawal` therefore decodes the ABI array offset (`0x20`) as the request id, not the actual Lido request id. The queue claim should then revert or target the wrong request, while `pendingRedemptions` remains nonzero and `report()` remains blocked by `require(pendingRedemptions == 0)` (`src/BaseLSTAccumulator.sol:146-147`, `src/BaseLSTAccumulator.sol:269-272`).

Impact x Likelihood: Medium impact because the normal management-to-keeper claim handoff can fail and strand the strategy in the pending-redemption state until operators use `manualClaimWithdrawals` or `clearPendingRedemptions`; Medium likelihood because the API returns bytes from initiate and accepts bytes for claim, which strongly suggests those bytes are round-trippable.

### MEDIUM - Strategy4626 deposits into the ERC4626 vault without requiring nonzero shares

`Strategy4626._stake` wraps all stETH into wstETH and calls `vault.deposit(wstETHBalance, address(this))` without checking the returned share amount (`src/Strategy4626.sol:32-42`). Inherited TokenizedStrategy accounting then credits the original WETH `assets` and mints strategy shares after `_deployFunds` returns (`lib/tokenized-strategy/src/TokenizedStrategy.sol:963-975`). A compliant ERC4626 deposit can return zero or dust shares under rounding or inflation conditions; OZ's reference ERC4626 computes shares with rounding down and does not require `shares != 0` in `deposit` (`lib/openzeppelin-contracts/contracts/token/ERC20/extensions/ERC4626.sol:153-159`, `lib/openzeppelin-contracts/contracts/token/ERC20/extensions/ERC4626.sol:199-200`). Strategy4626 later values the vault position from `vault.balanceOf(address(this))` and `vault.convertToAssets(...)` (`src/Strategy4626.sol:69-74`), so zero shares means the deposited wstETH is lost/donated while the depositor initially receives strategy shares against credited WETH.

Impact x Likelihood: High impact for deposits routed into an inflated or fee-heavy vault because user principal can be donated and later realized as strategy loss; Low-to-Medium likelihood because the vault is selected at strategy deployment and must be a wstETH ERC4626 vault, but ERC4626 rounding/inflation is a known integration edge. A minimum share check, or preview/min-share slippage guard, would make the integration fail closed.

## Non-Findings / Rejected Ideas

- INFO - Slither `Strategy4626Factory.newStrategy4626` reentrancy warning is not exploitable under the intended WETH/wstETH setup. `ERC20(_vault).symbol()` and `IERC4626(_vault).asset()` are view/static calls (`src/Strategy4626Factory.sol:48`, `src/Strategy4626.sol:21`). The constructor's spender approval to the vault is an approval on fixed wstETH and does not call the spender (`src/Strategy4626.sol:26`). The subsequent external calls are to the known freshly deployed Strategy4626 setters (`src/Strategy4626Factory.sol:52-64`) and do not call back into the vault. The mapping write after those calls is untidy for scanners but did not expose a duplicate-deployment path in this code flow (`src/Strategy4626Factory.sol:68`).
- INFO - Slither `Strategy.manualClaimWithdrawals` reentrancy warning is benign for the fixed Lido queue path. The external call precedes the optional `pendingRedemptions = 0` write (`src/Strategy.sol:116-125`), but the function is emergency-authorized, the external callee is the hard-coded Lido withdrawal queue, and any callback from the queue would not satisfy local management/keeper/emergency role checks (`lib/tokenized-strategy/src/TokenizedStrategy.sol:306-338`). The unrestricted `receive()` can only accept ETH (`src/Strategy.sol:36`).
- INFO - Public deposit/mint/withdraw/redeem/report/tend/emergencyWithdraw reentrancy is covered by TokenizedStrategy's `nonReentrant` guard (`lib/tokenized-strategy/src/TokenizedStrategy.sol:283-295`, `lib/tokenized-strategy/src/TokenizedStrategy.sol:487-635`, `lib/tokenized-strategy/src/TokenizedStrategy.sol:1081-1096`, `lib/tokenized-strategy/src/TokenizedStrategy.sol:1314-1358`). Local management/emergency functions are not independently guarded, but their callbacks would need to come from fixed protocol contracts or from the selected ERC4626 vault and still pass role checks for privileged functions.
- INFO - ERC777 and no-return ERC20 behavior on the strategy asset is not a live issue for the intended WETH asset. Inherited deposits pull the asset before minting shares and all public ERC4626 writes are nonreentrant (`lib/tokenized-strategy/src/TokenizedStrategy.sol:963-975`). OZ SafeERC20 handles optional return values for asset transfers (`lib/openzeppelin-contracts/contracts/token/ERC20/utils/SafeERC20.sol:26-35`, `lib/openzeppelin-contracts/contracts/token/ERC20/utils/SafeERC20.sol:117-123`). Fee-on-transfer, blacklist, or pausable generic ERC20 assets are outside the WETH-specific strategy assumptions because `_stake` requires WETH `withdraw`/`deposit` semantics (`src/Strategy.sol:55`, `src/Strategy.sol:81`).
- INFO - stETH/wstETH rebasing specifics are handled by reading balances/conversions at report time. stETH value defaults to current `balanceOf` (`src/BaseLSTAccumulator.sol:185-191`), and Strategy4626 values wstETH plus vault assets via wstETH conversion (`src/Strategy4626.sol:69-74`). Positive rebases become reportable profit and adverse changes become reportable loss, subject to health checks (`lib/tokenized-strategy-periphery/src/Bases/HealthCheck/BaseHealthCheck.sol:136-155`).
- INFO - Curve quote manipulation on WETH-to-stETH staking is limited by the execution minimum. The strategy only chooses Curve when `get_dy` is above the input amount, but the actual swap still uses `_min_to_amount = amount` and otherwise reverts instead of accepting below-1:1 stETH (`src/Strategy.sol:57-68`). Management stETH-to-WETH swaps use the management-supplied `_minOut` (`src/BaseLSTAccumulator.sol:241-245`, `src/Strategy.sol:74-81`).
- INFO - Forced ETH or direct ETH sends are donations, not an accounting bypass in the reviewed flows. Single-request claim records the ETH delta around `claimWithdrawal` (`src/Strategy.sol:107-109`) and then wraps the full balance (`src/Strategy.sol:111-112`); manual batch claim also wraps the full balance (`src/Strategy.sol:120-125`). Pre-existing ETH therefore becomes WETH held by the strategy rather than being lost.
- INFO - Unlimited approvals are broad but align with fixed-protocol or selected-vault trust assumptions. Curve receives WETH/stETH approvals (`src/Strategy.sol:33`, `src/Strategy.sol:75`), the Lido queue receives exact stETH approval per request (`src/Strategy.sol:92`), wstETH receives max stETH approval, and the selected vault receives max wstETH approval (`src/Strategy4626.sol:25-26`). A malicious selected vault could already mis-handle deposits/redeems, so the approval is not a separate privilege escalation beyond the vault trust boundary.
